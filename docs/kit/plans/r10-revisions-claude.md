### R1: Legacy-global apps cannot do what M8, M9 and M11 promise
- **Why:** PlayMaker's browser code reads and writes through `supabase-js` with the person's Supabase Auth session (`playmaker/src/lib/supabase.ts`, imported across 58 source files). PlayMaker's agent seam works only because PostgREST accepts the JWT PlayMaker mints with the legacy secret, which sets `auth.uid()` to the agent's own `auth.users` row (`playmaker/netlify/functions/lib/agentJwt.ts`). Three things in the plan therefore fail as written. First, M9's identity-origin sign-in path cannot give PlayMaker the Supabase session it needs, because that would put the Auth-administration secret online, and section 2.3b forbids that. Second, the plan never says which credential a legacy app's Function presents to the broker. Third, after M11 revokes the legacy secret, nothing outside Supabase Auth can mint a token that PostgREST accepts, so the plan has no working agent path for PlayMaker. This revision drops the unbuildable sign-in path, names the legacy credential, and gives the agent path one concrete mechanism.

### R2: Browser sessions need no refresh credential; an AI partner needs exactly one
- **Why:** Strict refresh rotation on browser cookies breaks ordinary use. Two tabs, or two parallel requests, refresh at once; the second presents a consumed generation, so the broker marks the family compromised and signs the person out. The rotation buys nothing for browsers, because the broker already checks every browser session online against `soma.browser_sessions`, which has idle and absolute expiry. For agents, the refresh family is keyed by `app_id` and `grant_id`, and a device code is bound to one app. That contradicts the section 0 decision "register the AI partner once, grant per app": a second app's pairing creates a second partner. It also leaves `app_id='*'` grants with no way to obtain a token for a second app. Finally, "revocation revokes the refresh family" would cut the AI off from every app when the person revokes one app's grant.
- **Change:**

```diff
@@ section 2.2, step 11
-11. The function sets broker-issued access and rotating refresh handles in `__Host-` prefixed, `HttpOnly`, `Secure`, `SameSite=Lax` cookies. The broker stores only keyed hashes of those handles. The function does not expose a Supabase Data API JWT to browser JavaScript. The browser obtains the pairwise identity and consented fields through the same-origin `/api/soma/v1/me` route.
+11. The function sets one broker-issued session handle in a `__Host-` prefixed, `HttpOnly`, `Secure`, `SameSite=Lax` cookie. ### R5: Nothing can execute an irreversible action after its cool-off
```
- **Why:** The plan says the server executes an irreversible intent "after the cool-off step has elapsed without the person cancelling". No request exists at that moment to run it. An app Function runs only inside a request, the plan defines no scheduled executor for app effects, and the AI's `GET` poll must not cause an effect. The fix makes the person's second confirmation the trigger. It needs no new machinery, and it is what a cool-off means to a person anyway.
- **Change:**

- **Why:** Step 4 says `register` mints credentials "for each broker (staging and production)", while step 5 and the second-app test register one environment at a time with `--environment`. A staging registration cannot mint production credentials, because the production broker has no record of the app until a production registration. It also must not mint them, because the second-app test runs against staging only.
- **Change:**

```diff
@@ section 2.4a, register step 4
-4. Mints overlapping runtime installation credentials and a release credential for each broker (staging and production) and writes them to the app's Netlify environment through the Netlify API, scoped so that only Functions read runtime credentials and only Builds read the release credential. Only production and the fixed `preview` branch receive SOMA credentials.
+4. Mints overlapping runtime installation credentials and a release credential from the broker of the environment being registered (step 5), and writes them through the Netlify API to the matching deploy context only: the `production` context for production, and the `preview` branch context for staging. Only Functions read runtime credentials, and only Builds read the release credential. Only production and the fixed `preview` branch receive SOMA credentials.
```

### R9: Remove the v0 leftover `identity.mode` from the canonical example
- **Why:** `"mode": "shared-soma"` appears only in the section 3.1 example. It is the v0 field `identity_project` ("soma_profiles is ALWAYS shared", `packages/soma-scaffolder/schema/soma-app.schema.json`), and nothing in v1 defines or reads it. `identity.subject` carries the meaning now. Because every unclassified manifest field joins the privileged projection, an undefined field in the canonical example becomes policy that nobody can explain.
- **Change:**

```diff
@@ section 3.1, example manifest
   "identity": {
-    "mode": "shared-soma",
     "subject": "pairwise",
     "admission": "open",
     "profile_fields": ["display_name", "locale"]
   },
```

`soma-scaffold migrate-spec` reports the v0 `identity_project` as an unmapped field rather than translating it.
